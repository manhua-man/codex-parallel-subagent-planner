# 请求链路

本文说明 `parallel-subagent-planner` 在一次 Codex 请求中的位置。这个 skill 不是 runtime 组件、本地 runner、Python 包、CLI 或 session manager。它由 Codex 加载为指令，用来指导主线程判断是否拆分、是否启动子智能体，以及如何做最终集成。

## 宿主链路位置

```text
用户输入
  |
  v
Codex CLI / app 解析请求
  |
  v
Codex 创建或恢复 agent session
  |
  +--> 加载 settings / skills / extensions
  |      |
  |      v
  |   parallel-subagent-planner 作为 skill 可用
  |
  +--> 恢复 session 状态
  |
  +--> 组装内置 tools
  |
  v
Agent loop
  |
  v
LLM 判断这个 skill 是否适用
  |
  +--> 不适用：主线程直接处理任务
  |
  +--> 适用：主线程按下面的 skill flow 执行
```

## 项目级循环

项目模式每次只启动一个依赖已满足的并行前沿：

```text
完整的范围内产品表面
  |
  v
模块矩阵 + 依赖图 + 共享契约 owner
  |
  v
当前并行前沿
  |
  v
启动最小但有价值的 wave
  |
  v
收集 + 检查 + 集成 + 契约验证
  |
  v
更新模块状态和依赖边
  |
  +--> 还有必需模块：重新计算前沿并继续
  |
  +--> 全部集成：主线程只跑一次最终全量验证
```

即使当前只能启动 Wave 0，也必须登记所有重要模块，不能只实现眼前第一个模块而不分析剩余产品范围。

## 职责边界

Codex 负责：

- 加载 skill 到上下文
- 提供真实的子智能体启动能力
- 在判定模型路由不可用前解析宿主提供的全部发车适配器；在 Codex Desktop 中，即使通用 `spawn_agent` 没有模型字段，已获授权的新 lane 仍可使用 `create_thread(model, thinking, target)`
- 管理 session、tools、文件访问和终端执行
- 渲染最终回复

这个 skill 负责指导：

- 当前请求属于单任务还是项目级目标
- 如何发现范围内的模块图和共享契约 ownership
- 是否应该考虑子智能体
- 哪些 lane 足够安全、值得启动
- 哪些 lane 应该 hold、合并或留在主线程
- 哪些模块属于当前并行前沿和后续 wave
- 每个子智能体拿到什么 compact context
- 每个子智能体可以读写哪些范围
- 子智能体结果如何集成和验证
- 每个项目 wave 完成后如何重新计算并行前沿
- 什么时候询问用户是否沉淀可复用子智能体角色

它把产品需求、已审查计划、架构决策和 OpenSpec tasks 当作输入，不替代这些工作流，也不负责选择外部 coding-agent backend。

## 强制长期 Agent 检查

每次 parallel run 结束后，主线程都要检查有没有已完成的子智能体角色值得沉淀成长期 agent。如果有可复用候选，主线程主动问用户是否要 promote。

输出只应该说明：

- 这个角色值不值得沉淀
- 为什么值得
- agent spec 建议存放在哪里

在用户明确批准具体 promotion 之前，不要创建或写入 `.codex/agents/` 或 `agents/` 文件。

## 非目标

本仓库不提供：

- Python 包
- CLI
- 本地 task runner
- session manager
- Codex 子智能体启动能力的替代品
- 未经明确批准自动创建 `.codex/agents/` 或 `agents/` 文件
- 产品需求、CEO/设计/工程计划审查或架构批准
- OpenSpec proposal/task ownership
- 外部 coding-agent backend 或 session 路由
